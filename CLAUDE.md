# Zom's MRP

Zom's MRP (Mission Ready Planner) is a ZomBeatz Media app for scheduling helicopter missions: aircraft by tail number, pilots rotating through hitches, maintainers, maintenance and training. React + TypeScript + Vite, built like Zomello.

- **Design and wording:** follow the ZomBeatz design system: https://github.com/ZomBeatz/zombeatz-docs/blob/main/design/DESIGN.md (locally `../zombeatz-docs/design/`). `src/tokens.css` is a copy of its `tokens.css`; build styles from the `--zb-*` variables.
- **Data** stays on one device for now: one JSON document in the browser's storage (`src/store.ts`). The demo lives in its own slot and never touches the person's own data.
- **Words:** the app says **client** for a `Mission`, **job** for a `Season`, **qualification** for a `Training`, **work order** for a `MaintenanceJob`, **line of business** for a `WorkType` and **schedule limitations** for a `RuleSet`; code, saved data and the import sheets keep the old names.
- **Missions are customers; seasons are dates.** A `Mission` holds what stays the same (name, contact, look, training, crew via `Person.missionIds`). Each `Season` is one stretch of dates on one aircraft; shifts point at seasons. Pages and checks work with `bookings(data)` from `src/bookings.ts` (a season joined with its mission). Older saves are converted in `src/migrate.ts`; add to it when the data changes shape.
- **Fleet first.** The Fleet page (`src/pages/Aircraft.tsx`, logic in `src/fleet.ts`) is the main view of what can be supported. Timelines share `src/components/timeline.tsx`. Aircraft types and equipment have their own page (`src/pages/Types.tsx`, logic in `src/aircraftTypes.ts`); tails, ratings and programs name their type, so `withTypes` keeps the list in step on every change and `renameType` carries a rename through.
- **Job requirements connect it all.** A client (`Mission`) holds default job requirements (qualifications, equipment, schedule limitations, `jobDefaults` for crew); a job (`Season`) can have its own (`requiredTrainingIds`, `requiredEquipmentIds`, `ruleSetId`), joined in `bookings()`. `requiredTraining(data, booking, role)` adds what everyone in the role and the job's aircraft types need; `jobLimits` gives a job's duty, rest and flight limits. Lines of business (`WorkType.defaults`) load into a new client. Prebuilt qualifications, equipment, schedule limitations and lines of business are in `src/library.ts`; `crewCheck` (coverage.ts) says who can work a job and what the rest are missing.
- **Training is set by missions.** People only need the training of the missions they work (`Person.missionIds`) or are booked on (`neededTraining` in `src/coverage.ts`). Certificates, medicals and check rides are trainings too (`kind`, logic in `src/certificates.ts`); one marked `everyone` is needed by its whole role on every booking. Medicals work out their expiry from class, exam date, the pilot's date of birth and the privileges needed (`medicalExpiry`, FAA 14 CFR 61.23; airline transport privileges are supported in code only). Attached files stay on the device (`src/docs.ts`) and go into backups.
- **Everything is whole days.** Starts are midnights and ends are the midnight after the last day. Use the calendar helpers in `src/time.ts` (`dayAt`, `dateToStart`, `dateToEnd`), never fixed 24-hour steps, so days that change the clock still line up.
- **Checks** (gaps, double bookings, qualifications, training, hitch length) are pure functions in `src/coverage.ts` with tests in `src/coverage.test.ts`. Add a test when you add a check.
- **Three builds of one app.** The web/desktop app (`npm run build`), the online demo (`VITE_DEMO=1`, GitHub Pages) and the server's app (`npm run build:server`, `VITE_SERVER=1`, built into `server/`). Data goes through `src/backends/`; the demo always stays in the browser.
- **Help** lives in three places that point at each other: the in-app Guide (`src/pages/Guide.tsx`), the online guide at docs.zombeatzmedia.com/mrp (the `zombeatz-docs` repository, `site/mrp/`), and `src/help.ts`, which maps pages and Guide sections to their docs pages for Find, the Guide's links and the notes on new pages. When a feature changes, update its docs page too; when a page is new, add it to `NEW_PAGE_NOTES`.
- **Demo data and the lessons and tours** are only in the online demo for now (`withDemo` in `src/platform.ts`); the app itself opens empty, with the setup steps on the Overview. The Guide is in every build.
- **The desktop app** (`src-tauri/`, Tauri 2) keeps the plan in `mrp.json` in the app data folder, which is named after the identifier `com.zombeatz.zoms-mrp`: never change it, or updates would start empty. Saving goes through five commands listed in `build.rs`; add a command there and in `capabilities/default.json`. Installers come from the "Desktop app" workflow on a `v*` tag; the Mac app is ad-hoc signed unless the Apple secrets in the README are set. `tauri.windows.conf.json` names the Windows app with a curly apostrophe (Zom’s), because a straight one breaks the NSIS installer script.
- **The server** (`server/`, Rust: axum, SQLite, Argon2) keeps the plan as one versioned document. Any change to sign-in, roles or headers needs a test in `server/src/tests.rs`; see SECURITY.md for what it promises.
- Run `npm run dev` (port 1430), `npm test`, and `npm run build` before calling something done; for the server also `npm run build:server && cargo test --manifest-path server/Cargo.toml`.
